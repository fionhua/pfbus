PocketFleet Meeting Lifecycle and Orchestration Specification (v1.1)

[Core Architectural Principles]
This specification is completely decoupled from the PFBus General Communication Protocol (v1.4):
1. The PFBus Protocol specification governs underlying syntax (how messages are sent, envelope format, semantics of routing fields);
2. This specification governs upper-layer lifecycles and collaboration workflows (when to start, when to dispatch tasks, permission gates, and how to conclude);
3. The PFBus Protocol specification is delivered only once prior to the meeting; subsequent task dispatches contain only current tasks and dynamic return credentials, strictly avoiding repetitive syntax reiteration.

--------------------------------------------------------------------------------
[Lifecycle State Transition Diagram]
IDLE State
  │  Human sends /meet [topic] in Telegram group
  ▼
Roll-Call Preparation Phase (PREP · Max 30s)
  │  Deliver v1.4 spec and invitation ➔ Nodes reply [PFBus][signup:%s] ➔ Host present & quorum >= 2
  ▼
Rule Publication Phase (RULES)
  │  Push briefing to Host ➔ Host AI emits [PFBus]/rules ➔ Bridge broadcasts Start Clearance & score cap
  ▼
Deliberation & Collaboration Phase (ACTIVE)
  │  Host AI dispatches tasks upon Start Clearance ➔ Nodes execute and return ➔ Cross-audit and synthesis
  ▼
Settlement & Adjournment Phase (CLOSED)
  │  Host or Human emits [PFBus]/meetover ➔ Stop new dispatches & drain pending ➔ Broadcast closing card
  ▼
Return to IDLE State

--------------------------------------------------------------------------------
[Detailed Phase Execution Specifications]

Phase 1: Roll-Call Preparation Phase (PREP · Max 30 Seconds)
1. Trigger Condition: Human sends /meet <topic> in Telegram group (or clicks "Start Meeting" in client UI).
2. Bridge Actions (Pre-meeting Protocol & Roll-Call Delivery):
   - Protocol Delivery (Once per meeting): Task ticket for Code AI includes local file path (file:///.../PFBusProtocol_v1.4.txt); Web Dialog AI is injected with v1.4 plain text.
   - Roll-Call Broadcast: Dispatches topic and attendance invitation to candidate seats.
3. Node Actions:
   - Participating nodes output on the first line: [PFBus][signup:YourNickname], optionally followed by a brief readiness note on the next line.
   - Code AI Admission Pre-verification: Code AI must read the local protocol file and verify comprehension of communication syntax before executing signup return.
4. Defensive Guardrails (Admission Qualification Gating):
   - Silent Attendance: The Bridge only updates the "Seat Readiness Status Card" in the Telegram group, silently recording attendance without flooding the group with individual receipts.
   - 30-Second Cutoff: Attendance closes immediately when all invited members arrive or upon 30 seconds timeout, locking the official "Actual Attendance List".
   - Minimum Legal Quorum: Host must be present and total attendees >= 2 (Host + at least 1 participant). If Host is absent or quorum < 2 at the 30s cutoff, Bridge terminates meeting with failure notification, strictly prohibiting empty idling in RULES.

Phase 2: Rules and Start Clearance Gating (RULES · Host-Guest Decoupling)
1. Trigger Condition: PREP phase ends with legal quorum met; Bridge delivers "Meeting Briefing" to Host seat (including actual attendance list).
2. Host AI Actions:
   - Prohibition of Pointless Inquiries: If Human topic already contains specific goals and scope, Host AI must generate /rules directly, strictly forbidden from wasting a turn asking Human for known information.
   - Emits the three task essentials and assignment directives:
     [PFBus]/rules
     {"goal":"<topic goal>","deliverables":["<deliverables>"],"acceptance_criteria":["<criteria>"],"assignments":[{"seat":"@NodeName","duty":"<duty>"}]}
3. Bridge Actions (Gating & Score Cap Lock):
   - Validates rule syntax and transparently maps "seat" natural names to physical seats;
   - Locks contribution score cap: Score Cap = Participating Node Count x 10 points;
   - Broadcasts to all seats: [PocketFleet · Assembly Concluded · Start Clearance].
4. Defensive Guardrails (Start Clearance Gating & State Persistence):
   - Strict Anti-Preemption: Prior to official issuance of Start Clearance, no node (including Host) may dispatch tasks; Host must verify receipt of Start Clearance before initiating round 1 task dispatches.
   - Gating State Persistence: Start Clearance is persisted by the Bridge layer. If lost due to network fluctuations, AI may recover via status inquiry; gating state is not reset by transient message loss.

Phase 3: Autonomous Deliberation & Advancement (ACTIVE · Streamlined Ticket Flow)
1. Outbound Communication:
   - Strictly conforms to PFBus v1.4 general format: [PFBus][mailto:@NodeName];[cc:...];[waitReply|noReply].
   - Each round's task ticket carries only two components: 1) Specific tasks and discussion content for the current round; 2) Return credentials for this round (Code AI includes dynamic IPC URL).
   - Redundant lectures on "how to format envelopes" are strictly prohibited in task tickets.
2. Collaboration & Concurrency:
   - Single-Round Multi-Envelope Parallelism: The Host may emit multiple independent [PFBus] envelopes in a single turn; Bridge unpacks and delivers them concurrently to their respective targets.
   - Queue Release Iron Law: Code AI, whether receiving waitReply or noReply, must execute a curl return after finishing work to release its local IPC queue.

Phase 4: Synthesis, Settlement & Adjournment (CLOSED · Graceful Shutdown)
1. Trigger Condition:
   - Planned deliverables completed and acceptance criteria verified;
   - Host AI (or Human) emits adjournment command in message body.
2. Adjournment Outbound Format:
   [PFBus]/meetover
   [Final Acceptance Report]
   1. Deliverables list and physical paths (file paths / git PR / artifact locations): ...
   2. Outstanding issues & unverified items (must declare truthfully; claiming unverified items as completed is strictly forbidden): ...
   3. Node strategic contribution ratings (0-10 points per node; no need to force-fill to cap):
      - @NodeA: 9 points (completed core technical breakthrough)
      - @NodeB: 0 points (simple agreement, no independent contribution)
3. Bridge Actions (Three-Step Graceful Shutdown · Data Integrity Protection):
   - 1) Block New Dispatches: Upon capturing /meetover, Bridge immediately rejects any further dispatches, halting task proliferation;
   - 2) In-Flight Task Drain: Waits for in-flight asynchronous tasks or returns (with a short timeout), ensuring final execution results are safely persisted and not abruptly truncated;
   - 3) Site Cleanup: Generates single final settlement card pinned in Telegram group, revokes temporary buttons, releases all seat leases, and returns system completely to IDLE state.
