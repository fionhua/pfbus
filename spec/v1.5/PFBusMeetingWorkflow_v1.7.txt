PocketFleet Meeting Lifecycle and Orchestration Specification (v1.7 · Minimal Fail-Safe Final Edition)

[Core Architectural Principles]
This specification is completely decoupled from the PFBus General Communication Protocol (v1.4):
1. The PFBus Protocol specification governs underlying syntax (how messages are sent, envelope format, semantics of routing fields);
2. This specification governs upper-layer lifecycles and collaboration workflows (when to start, when to dispatch tasks, permission gates, and how to conclude);
3. The PFBus Protocol specification is delivered only once prior to the meeting; subsequent task dispatches contain only current tasks and dynamic return credentials, strictly avoiding repetitive syntax reiteration.

[Starfleet Human-AI Collaboration Iron Law (Human speech unfinished, AI do not preempt)]
Humans typically present problems incrementally in segments and will never prepay the cognitive cost of lengthy topics when attendee availability is still unknown.
Therefore, it is strictly required: Human initiates with a simple /meet ➔ 60s roll-call verifies attendance ➔ Once quorum is established, Host initiates opening inquiry to Human ➔ Human reviews actual lineup and calmly dispatches topic ➔ Host synthesizes and emits rules.

[Streamlined Lifecycle Mainline]
Human /meet ➔ Single Roll-Call(60s) ➔ Quorum Verification ➔ Host Opening Inquiry ➔ Human Topic Dispatch ➔ Host Rules Submission ➔ Directed Clearance ➔ Dispatch & Return ➔ In-Place Settlement

  │  Human sends /meet in group (pure command, zero prepay burden) or clicks launch on desktop
  ▼
Roll-Call Preparation Phase (PREP · Max 60s)
  │  Deliver v1.4 spec and invitation ➔ Nodes reply [PFBus][signup:%s] ➔ Verify liveness & quorum
  ▼
Host Opening Inquiry & Rule Publication Phase (RULES)
  │  Lineup ready ➔ Host opening inquiry ➔ Human dispatches topic ➔ Host emits [PFBus]/rules ➔ Clearance to Host only
  ▼

  │  Cross-seat parallel / Single-seat queued ➔ Nodes execute and return ➔ Watchdog circuit breaking
  ▼
Settlement & Adjournment Phase (CLOSED)
  │  Host finishes or Human aborts ➔ In-place refresh of settlement card ➔ Release all seat leases
  ▼
Return to IDLE State

[Detailed Phase Execution Specifications]

Phase 1: Roll-Call Preparation Phase (PREP · Max 60 Seconds · Zero Prepay Cost)
1. Trigger Condition:
   - Human sends /meet in Telegram group (pure command, never requiring a lengthy topic);
   - Or clicks "Start Meeting" button in client desktop UI.
2. Bridge Actions (Pre-meeting Protocol & Roll-Call Delivery):
   - Protocol Delivery (Once per meeting): Task ticket for Code AI includes local file path (file:///.../PFBusProtocol_v1.4.txt); Web Dialog AI is injected with v1.4 plain text.
   - Roll-Call Broadcast: Dispatches attendance invitation to candidate seats (only confirming "can attend", triggering zero substantive cognitive load, zero token waste).
3. Node Actions:
   - Participating nodes output on the first line: [PFBus][signup:YourNickname], strictly following the two-line format with 8-character readiness declaration.
   - Code AI Admission Pre-verification: Code AI must read the local protocol file and verify comprehension of communication syntax before executing signup return.
4. Defensive Guardrails (Admission Qualification & Failure Exit):
   - Silent Attendance: The Bridge only updates the "Seat Readiness Status Card" in-place in Telegram, strictly prohibiting flood receipts in group chat.
   - 60-Second Cutoff: Attendance closes immediately when all members arrive or upon 60 seconds timeout, locking the official "Actual Attendance List" (absent nodes marked red and purged on status card).
   - Failure Exit: If Host is absent or quorum < 2 at the 60s cutoff, Bridge reports clearly on the status card with "Re-elect Host" and "Cancel Meeting" buttons, preventing meetings from getting stuck in preparation. Humans incur zero sunk cost.

Phase 2: Host Opening Inquiry & Rule Gating (RULES · Human speech unfinished, AI do not preempt)
1. Trigger Condition: PREP ends with legal quorum met (Host present and total count >= 2), proving meeting conditions are genuinely satisfied.
2. Host Opening Inquiry:
   - Bridge delivers "Meeting Briefing" to Host (including actual attendance list);
   - Host initiates [Opening Inquiry] to all humans: reports attendee lineup and formally invites Human to dispatch topic.
3. Human Topic Dispatch & Discussion:
   - Human, seeing actual attendee lineup, calmly delivers topic, background materials, and expectations in group (allowing incremental, segment-by-segment elaboration);
   - Uphold "Human speech unfinished, AI do not preempt": before Human delivers explicit task conclusions, AI only listens and confirms, never preemptively dispatching tasks.
4. Host Rule Synthesis & Emission:
   - After Human completes topic presentation, Host AI synthesizes Human intent into three task essentials and assignment directives:
     [PFBus]/rules
     {"goal":"<topic goal>","deliverables":["<deliverables>"],"acceptance_criteria":["<criteria>"],"assignments":[{"seat":"@NodeName","duty":"<duty>"}]}
5. Bridge Actions (Directed Clearance · Full Broadcast Prohibited):
   - Validates rule syntax and transparently maps "seat" natural names to physical seats;
   - Directed Clearance to Host ONLY: Bridge delivers [Start Clearance] exclusively to Host AI; other seats learn overall goals and duties upon receiving their first task dispatch.
6. Defensive Guardrails (Start Clearance Gating & State Persistence):
   - Strict Anti-Preemption: Prior to receiving Start Clearance, Host may not dispatch tasks; gating state is persisted by Bridge and recoverable across disconnections.

Phase 3: Autonomous Deliberation & Advancement (ACTIVE · Independent Parallelism & Single-Seat Queueing)
1. Outbound Communication:
   - Strictly conforms to PFBus v1.4 general format: [PFBus][mailto:@NodeName];[cc:...];[waitReply|noReply].
   - Each round's task ticket carries only two components: 1) Current task and discussion content; 2) Return credentials for this round (dynamic IPC URL).
2. Concurrency and Queue Isolation (Ticket Collision Prevention):
   - Cross-Seat Parallelism: Different physical seats are fully concurrent; Host may emit multiple independent [PFBus] envelopes in a single turn for concurrent distribution;
   - Single-Seat Queueing: Tasks for the same physical session or shared return file (./{node_name}meeting_info.txt) must strictly queue FIFO, eliminating concurrency collisions;
   - Precise Ticket Alignment: Timeout does not mean task cancellation; late receipts only claim original ticket IDs, strictly preventing replay collisions.
3. Defensive Guardrails (Meeting Circuit Breaking & Convergence Urging):
   - Bridge has built-in meeting thresholds (default max 6 rounds or 180s without progress per seat); round 5 automatically injects [Convergence Reminder] to Host, preventing infinite loops.

Phase 4: Synthesis, Settlement & Adjournment (CLOSED · Multi-Path Closure)
1. Trigger Condition (Dual Paths Supported):
   - Normal Closure: Deliverables completed and acceptance verified; Host AI emits [PFBus]/meetover;
   - Abnormal Closure: Tasks blocked or Human sends /meetover / clicks "Terminate Meeting" at any time (supports partial settlement).
2. Adjournment Outbound Format:
   [PFBus]/meetover
   [Final Acceptance Report]
   1. Deliverables: ...
   2. Pending Verification: ...
   3. Contribution Ratings:
      - @NodeA: 9 points, completed core technical breakthrough
      - @NodeB: 0 points, no independent output
3. Bridge Actions (In-Place Settlement & Graceful Shutdown):
   - Persistence Priority: Bridge safely writes deliverables and unverified items to disk before revoking leases, ensuring no results are lost if card sending fails;
   - In-Place Refresh: In Telegram group, refreshes original status card in-place into final settlement card, revokes temporary keyboard, avoiding multi-report spam;
   - Complete Cleanup: Releases all seat allocations; system returns smoothly to normal dialogue state.

[Appendix: Standard Outbound Script Templates for Participating AI (Crafted by Xinji Shu · Minimal Fail-Safe Final Edition)]
(Note: Bridge system prompts are assembled in Go backend code; AI does not need to learn communication syntax details. Participating AI and Host AI strictly adhere to the following outbound templates)

Template 1: [signup] Seat Check-in Script (Participating AI Outbound)
Trigger: After receiving attendance invitation during PREP roll-call
Rule: Mandatory two lines, 8-character body, preventing collisions at the root
[PFBus][signup:{{nickname}}]
Ready, waiting to start.

Template 2: Opening Inquiry Script (Host AI -> Commander)
Trigger: After roll-call concludes and legal quorum is met
Tone: Crisp and commanding, no customer service fluff, conforming to the "Human speech unfinished, AI do not preempt" iron law

Actual attendees: {{seat_list}}. Lineup ready, please dispatch topic.
